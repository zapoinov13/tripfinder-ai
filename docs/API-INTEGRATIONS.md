# API-интеграции TourGo: фиды партнёров и агрегаторов

Как каталоги партнёров (туры, отели, авто, спорт) попадают на платформу
автоматически, и куда это развивается (cron, MCP).

## Архитектура

```
Источник партнёра/агрегатора          TourGo
┌───────────────────────────┐    ┌─────────────────────────────────────┐
│ JSON-фид по URL           │    │ Edge Function sync-supplier-feed    │
│ (Supplier Feed v1)        │───▶│  - серверный fetch (обходит CORS)   │
│ авторизация: api_key /    │    │  - передаёт ключи из подключения    │
│ basic / bearer            │    └──────────────┬──────────────────────┘
└───────────────────────────┘                   ▼
                                  parseSupplierFeed → applySupplierFeed
                                   - валидация, нормализация питания,
                                     направлений, дат
                                   - импорт новых туров
                                   - обновление цен/наличия
                                   - архив исчезнувших
                                                ▼
                                  syncLogs + статус подключения
                                  (журнал в админке «Мониторинг API»)
```

## Формат: TourGo Supplier Feed v1

Один JSON-документ (пример: `public/supplier-feed.example.json`, типы:
`src/lib/platform/supplier-feed.ts`):

```json
{
  "version": 1,
  "currency": "KZT",
  "updated_at": "2026-08-26T10:00:00Z",
  "tours": [
    {
      "external_id": "TC-1001",
      "title": "Дубай на майские",
      "hotel_name": "Rixos Premium Dubai",
      "price": 519000,
      "city": "Дубай",
      "from_city": "Алматы",
      "nights": 6,
      "meal": "AI",
      "date_start": "2026-05-01",
      "availability": 8,
      "status": "active",
      "photos": ["https://..."],
      "hot_deal": true
    }
  ]
}
```

Обязательные поля: `external_id`, `title`, `hotel_name`, `price`.
`external_id` — ключ идемпотентности: повторный импорт обновляет тур, а не
дублирует. Туры, пропавшие из фида, автоматически архивируются.

## Подключение (сторона партнёра)

Кабинет → Туры → «Добавить» → режим API: URL фида, тип авторизации, ключи,
интервал синхронизации. Кнопка «Проверить связь» и ручная синхронизация.

## Автосинхронизация

`src/lib/platform/api-sync.ts` — планировщик: раз в минуту проверяет,
у каких подключений истёк `syncIntervalMin`, и запускает sync.

- Работает, пока открыта админка (все подключения) или кабинет партнёра
  (только его компания).
- Ошибочные подключения ретраятся не чаще раза в 10 минут.
- Каждый прогон пишется в аудит (`api_auto_sync`) и в журнал синхронизаций.

## Добавление нового агрегатора

Адаптеры реализуют интерфейс `TourOperatorAdapter`
(`src/lib/platform-contracts`): `testConnection`, `getTours`,
`getAvailability`, `getPrices`, `createBooking`, `sync`. Сейчас один
универсальный адаптер (`MockOperatorAdapter`) читает Supplier Feed v1 —
для нового агрегатора с другим форматом пишется адаптер-переводчик его
формата в `SupplierFeedDocument`, остальной конвейер переиспользуется.

## Дорожная карта

1. **Серверный cron** — Edge Function по расписанию (Supabase Scheduled
   Functions) вызывает тот же конвейер, чтобы фиды тянулись без открытого
   браузера. Клиентский планировщик остаётся как ручной/фоновый дубль.
2. **MCP-сервер TourGo** — обёртка над теми же операциями (поиск туров,
   наличие, цены, создание заявки) в формате Model Context Protocol, чтобы
   AI-агенты партнёров и агрегаторов подключались к платформе напрямую.
   Инструменты 1:1 повторяют `TourOperatorAdapter`, поэтому серверная
   реализация переиспользует существующий код.
3. **Webhooks** — приём push-обновлений от крупных агрегаторов вместо
   опроса фида.
